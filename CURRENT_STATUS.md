## Publish failure classification and fail-fast retries (P1-03) — 2026-10-18

Provider failures are now normalized instead of blindly retried. The new shared module `src/publishers/failureClassification.ts` classifies every publish failure into one of six bounded codes — `credentials_invalid`, `permission_denied`, `rate_limited`, `payload_rejected`, `provider_unavailable`, `unknown` — decides retryability (invalid credentials, lost permissions, and rejected payloads are terminal; rate limits and provider outages retry; unknown stays retryable as the conservative default), converts provider retry-after hints into milliseconds, and sanitizes every operator-facing message (exact stored secret values, Telegram bot URLs, OAuth query credentials, and bearer headers) before it reaches job stores, dead-letters, lifecycle events, or the API.

The Telegram and YouTube publishers now classify their real provider errors: Telegram maps HTTP status plus API description (401 → `credentials_invalid`, 403 → `permission_denied`, 429 → `rate_limited` with `parameters.retry_after`, "chat not found"/"blocked" 400s → `permission_denied`, other 400s → `payload_rejected`, network errors → `provider_unavailable`) and returns structured `errorCode`/`retryAfterSeconds` on `PublishResult`; YouTube maps Gaxios status and googleapis error reasons (`quotaExceeded`/`rateLimitExceeded` → `rate_limited`, auth errors → `credentials_invalid`), redacting refresh-token and client-secret values. Publishers without a dedicated mapping still fail safe through the shared text inference.

`PublishWorker` now fails fast on non-retryable classes: `job.discard()` prevents BullMQ from scheduling a pointless retry, and the failed handler treats the single failure as terminal — dead-letter payloads carry `failureCode`, the publish job records `Terminal failure (<code>)`, and the release target reaches `failed` with `lastErrorCode` set to the normalized code. Lifecycle `failed` payloads now carry `{ error, code, terminal }`, and the DeadLetterWorker propagates `failureCode` into its lifecycle event and alert details. Local platform-limit validation failures are classified `payload_rejected` and no longer consume retry attempts. Rate limits are the one class that still retries: when a provider reports 429 with retry-after, the job is deferred with `moveToDelayed` for the provider's own delay, bounded to two deferrals that do not consume the attempt budget, then falls back to the standard 2-attempt/60s backoff contract.

Drill evidence (owner-provided credential, container rebuilt from this tree): target `target_f3ae276b-01ea-4962-b4c8-c521fa9991d1` was queued with an invalid-but-present credential. The worker logged `PublishWorker processing job` at 22:37:15.660 and the dead-letter line at 22:37:16.216 — one attempt, ~0.6s — with `failureCode: "credentials_invalid"`, `attemptsMade: 1`, and `failFast: true`; the DeadLetterWorker processed the record immediately. The target reached `failed` with `attempts: 1` and `lastErrorCode: "credentials_invalid"`, and the lifecycle timeline shows `publishing` → `failed` (payload `{ code: "credentials_invalid", terminal: true }`). A 75-second quiet window — longer than the 60s backoff — showed the attempt counter still at 1, proving no BullMQ retry was scheduled. The owner credential was rotated back (verify 200), operator recovery re-queued the failed target (HTTP 202), and the worker published exactly once (message id 13, target `published`, `attempts: 2`, `publishing` → `completed`); the drill message was deleted through the Bot API, and the final state is connector `connected`, destination `verified`, all six targets `published`.

## Backup, restore, and disaster-recovery rehearsal (G-09) — 2026-10-21

Backup and restore are now implemented and proven for the current file-backed production shape. The new `scripts/backup.mjs` creates a full data-directory archive — every JSON store, media artifacts, logs, and the encrypted connector-secret store — with a per-file size/SHA-256/mode manifest inside the archive. Temporary work files, caches, the re-provisionable `libs/` runtime, and nested backups are excluded; the deployment `.env` is never included. Archives are AES-256-CBC encrypted (PBKDF2, 200k iterations) by default: unencrypted output is refused unless `--allow-plaintext` is passed explicitly, because the auth store contains a legacy plaintext tenant key field. `--pause-container` stops the app for a consistent snapshot and restarts it in a `finally` block; `--keep N` prunes older archives and sidecars. `scripts/restore.mjs` is fail-closed: sidecar checksum, gzip/tar extraction, full manifest verification, an explicit target, and a pre-restore rename (`<target>.pre-restore-<stamp>`) as the rollback artifact. `scripts/backup.sh` is now a compatibility wrapper; the legacy `scripts/backupData.ts` is not a disaster-recovery backup. The operator runbook is `docs/BACKUP_RESTORE_RUNBOOK.md`.

Drill evidence (live local stack, owner Telegram connector, six published targets): an encrypted paused backup produced `content-factory-backup-2026-10-21T17-43-05-611Z.tar.gz.enc` (111,254,288 bytes, SHA-256 `ae1f1c95…b8e734e`) containing 52 files / 115,741,667 bytes; the app was healthy again 4.05 s after restart, and stop→archive took 9.6 s. Independent verification took 1.24 s with zero manifest mismatches and zero unexpected files. Restore to a staging directory took 2.4 s and reproduced all 32 JSON store SHA-256 hashes and all 5 video SHA-256 hashes (107,347,708 bytes) exactly. A disposable app instance booted against the restored data with `REDIS_ENABLED=false` on port 3124 (isolated from the live queue), was healthy in 4.02 s, authenticated with the restored tenant key, and returned connectors, releases, release details, and 6/6 published targets identical to the source (`sourceMatches: true`). Restore plus boot-to-verified RTO was 6.4 s; the whole drill took 25.3 s. The sandbox also proved plaintext refusal, non-empty-target refusal without `--force`, rollback-artifact creation with `--force`, mode preservation (secret files stay `0600`), and retention pruning with sidecar cleanup.

RPO for this scope is the operator's backup interval: a paused backup is a consistent point-in-time snapshot, but no schedule is installed by this repository. Limitations remain explicit: archives are local-only (no off-host replication), Redis/BullMQ transient queue state is not in the archive (durable job/release records are in JSON and re-enqueue through the operator recovery path), PostgreSQL/MinIO scope remains owner-gated and disabled, and a lost `BACKUP_PASSPHRASE` makes the archive unrecoverable. The `.env` and its `JWT_SECRET`/`TENANT_KEYS_SECRET` remain out-of-band operator secrets.
