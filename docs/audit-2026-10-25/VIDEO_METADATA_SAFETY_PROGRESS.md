# Video metadata persistence safety — twenty-seventh increment, 31 October 2026

Video metadata now uses exclusive initialization and private UUID staging with atomic replacement. Existing empty, malformed and invalid-identity files are preserved and rejected rather than reset. Rows must have a nonempty video ID and, when present, a nonempty workspace ID; duplicate workspace/video identities block reads and writes. Errors do not echo stored payloads.

The asynchronous upsert delegates to a complete synchronous read/modify/replace operation before yielding. Independent instances in one process therefore retain overlapping async and sync updates instead of overwriting an earlier snapshot. New writes require a workspace and video identity. Legacy ownerless rows are preserved during valid writes but stay out of scoped reads and deduplication; no ownership is inferred or assigned. Repeated video IDs in distinct workspaces remain separate identities.

Twelve new temporary-directory regressions cover corruption preservation, mixed concurrent writers, owned updates with legacy preservation, failed replacement cleanup and private permissions. The existing ShortCreator filesystem mock now implements exclusive creation and atomic rename semantics rather than overwriting initialized files. An initial full-suite attempt exposed those missing mock operations and one provider-test import timeout; the corrected video tests and provider regression passed together. No provider call or application-data operation was performed by this increment.

Final combined verification for increments 27–28 passed backend typecheck, **755 tests across 127 files**, production build and AST/build consistency for **353 registrations across 46 routers**. Changed-file ESLint and scoped whitespace checks passed. Full-repository lint remains an open baseline. Shared final evidence is `implementation-evidence/increments27-28-production-final.log` and `increments27-28-lint.log`; focused logs and hashes use this increment’s safety prefix. Tests use temporary stores, filesystem mocks and local provider stubs; no real application data or provider operation was changed.

This is file-mode coordination inside one Node process. Cross-process transactions, fsync/power-loss guarantees, durable migration, full metadata schema validation and restart recovery for an unknown producer outcome remain open. This prerequisite does not complete scheduler video reconciliation or close an audit phase.
